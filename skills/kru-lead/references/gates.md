# Review and verify — which gates a slice earns

Loaded by `lead` when the branch is live.

**A build return from a seat carrying Block O, with no `Return pass:` line, is unverified** — that line is the seat's own read-back of the finished slice (`${CURSOR_PLUGIN_ROOT}/skills/kru-roster/shared-blocks.md` → Block O), and its absence is the one defect every gate below is blind to, because a pass that never ran leaves no diff. Ask that seat for it — same-task reuse, inside the 2-loop cap — before the gates run. The brief never asks: the block rides in the seat prompt, and re-authoring it there is the restatement Step 3 refuses. The three seats Block O exempts (`kru-test-writer`, `kru-brand-designer`, `kru-ui-designer`) never carry the line; their own bound — a green suite, *Prove it at size*, the user's eye — is their verification.

**Done is judged on evidence, not the return's account of itself.** Before a build return counts as done, pair every behavior on the list you handed down (your grill, or `brief.md`'s `Done when` — the PM bot's done-check, and the oracle for the whole change) with its proof — a test name, a command's output, a count, a screenshot path, from the return or from your own scoped run. Those pairs are the **Proof** block of your report (`${CURSOR_PLUGIN_ROOT}/skills/kru-lead/SKILL.md` → *Report when work lands*), which is what the PM bot reviews. A behavior with no proof beside it is unbuilt until shown otherwise: send it back to that seat (same-task reuse, inside the 2-loop cap) before the gates below spend a review on it.

The review gates below are independent and read-only — batch the ones that only read source in one message (e.g. `kru-code-reviewer` + `kru-architecture-reviewer`), then merge their findings into one fix list for the builder. A seat that drives a browser or runs a suite fits the machine budget the session runs under (root `AGENTS.md`, or a `.cursor/rules` file with `alwaysApply: true`): the two browser-driving reviewers run one at a time, never beside each other or a suite. The fix→re-review loop is sequential.

**A finding enters the fix list only when its trigger happens in normal use** — an ordinary user action, a provider's documented retry or redelivery, concurrency the real crons, retries and staff produce, data a UI or an import can create, an ordinary attacker. One that needs a convoluted trigger is dropped, one counted line in the report at most, never ranked or filed: our own keys or config failing once set (a key a *user* enters still gets validated and a clear error), a provider breaking its own docs, one human action racing itself within milliseconds, data no path can create, an attacker already holding our secrets or database, a vendor outage cited to justify new machinery, or several of these stacked. The same bar holds wherever a defect gets filed or fixed.

**Scale the batch to live-versus-latent.** The full batch is priced for a slice shipping a path something reaches today. A slice that is entirely latent — a fix behind a trigger this codebase doesn't have yet, a cleanup of a path nothing calls — takes one reviewer or none: an adversarial multi-agent pass over it returns findings about code that cannot run, and spends the review a live slice needed.

**Name no report path in a review brief.** In this fork every review seat — `kru-code-reviewer`, `kru-architecture-reviewer`, `kru-accessibility-reviewer`, `kru-visual-reviewer`, `kru-ux-auditor` — runs with Cursor's `readonly` (no file edits, no state-changing shell), so it has nowhere to write the long half of its return. Its *What you return* contract carries the other branch: no path named → it returns inline under the same caps, the capped fix list first. `hooks/check-handoff.sh` supplies no path either. What outlives the run is unchanged: what you route (the fix list) and what you capture (`issues/<kebab-slug>.md`, Step 4.5) — never the return itself. When a batch is wide enough that six inline returns would crowd your context, run the seats in two smaller batches rather than lifting `readonly`.


**Hand down the intent, not only the diff.** A reviewer that gets files and a report path re-derives what the slice was *for* from the code that may have gotten it wrong — so it can catch *built wrong* and never *built the wrong thing*. Put the behavior list in the review brief: the one from your grill, or `brief.md`'s `Done when`, the same list the builder got (contract item 4, Step 3). It is the cheapest line in the brief and the only one that buys a whole class of finding.

- Structure: for a refactor or a new module boundary, spawn `kru-architecture-reviewer` in **design mode** BEFORE the builder (settle the seam/interface), and in **review mode** after (gate boundary integrity). Skip for trivial or purely additive changes.
- Correctness: spawn `kru-code-reviewer` — it reads for comment hygiene alongside the bugs. `/review` inline is the fast path for a small diff — it runs as a background subagent, and with no level given reuses the last one typed (say `/code-review high` to set it) — and reviews against AGENTS.md, never `shared-blocks.md`, so **the comment pass stays lead-owned**, the list in `SKILL.md` → *Delegate on stack, not size*: read the diff's added comments against `skills/kru-roster/shared-blocks.md` → Block I before you call the slice reviewed. `/review` itself is a background subagent, not this pass.
- **Mockup layout gate (before the PM).** Every screen mockup — a `.dc.html` artboard, a `/canvas` publish, or any rendered preview the lead would put in front of the PM — passes **`kru-visual-reviewer`** before the PM (or owner) sees it. **`kru-ui-designer` already runs `composition` → *The pass* on every artboard before publish**; that self-check is not the gate — the reviewer **renders and measures independently** and the drafter does not grade its own work. This is not the design verdict (that stays the PM's eye, below); it applies the **same composition relations** the pass checked — entries in `skills/kru-composition/reference/layout.md` (and `hierarchy.md` / `text.md` where the brief loads them) — with **selector or `file:line` and measured px**. **Existing-system repos too:** skipping the design hop for a build does not skip this gate when `kru-ui-designer` or `/kru-design` produces a new page or screen mockup.
  1. **Render.** Open each artboard in a real browser at **desktop 1440** and **mobile 375** (`local-browser` → `emulate`). Targets are the absolute `.dc.html` paths or the canvas URL. The lead serves `.design-work/` read-only when `file://` blocks fonts or images; **`kru-visual-reviewer` still never starts a server** — if nothing answers, it returns that gap and the lead fixes reachability before re-dispatch.
  2. **Brief mockup layout.** Hand `kru-visual-reviewer` the artboard list, both viewports, and **mockup layout** intent: verify the pass's **done-when** (every node's sibling gap > any internal gap) and **step 5** — every loaded `composition` entry, cited by section name. Findings carry **the entry violated**, **selector or `file:line`**, and **measured px** — not taste.
  3. **Loop.** **FIX** → brief `kru-ui-designer` to redraw from the on-disk artboards and re-publish if needed → re-run the reviewer. **Cap at three rounds.** After the cap, show the PM the draft **and** any open layout findings — do not block on perfection, but do not hide the list.
  4. **Then the PM channel.** Only after step 3 (clean **SHIP** on layout, or round 3 exhausted) hand the canvas card or `.dc.html` paths to the PM with the seat's design question. The PM's eye on the render remains the design gate; this gate only keeps failed composition checks from reaching them cold.


- Design work: **the gate is the PM bot's eye, and there is no substitute for it** — it judges the screenshots and paths in your Proof block, and takes the call to the owner only when it can't judge it — conformance to a design is a judgment, not a measurement (`${CURSOR_PLUGIN_ROOT}/references/ui-handoff.md`), so don't spend a browser sweep trying to replace it. Where the system is built from scratch this gate runs **twice, and the first run is the cheap one**: once on the canvas, where the look is settled before a line of app code exists (Step 2, *UI from scratch*), then on the feature builds, where what's in question is only whether the build honors it. What you *do* owe the second run is the thing that makes it short — the builder invented nothing, because the token file is a closed set and the repo's own gate says so at every commit. A **named gap** in the builder's return is the one output you act on before the PM looks: it goes to the **PM** as the visible choice ("what colour for warnings?"), not to a seat — the token name it would need stays in the record and the builder's brief. The PM reports back through you and you route each fix to the same builder (same-task reuse, inside the 2-loop cap), motion included — no separate motion gate.
- Screen passes: on UI work, spawn the two review-only seats after the source batch, one at a time — `kru-accessibility-reviewer` (structural WCAG: keyboard, focus, target size, name/role/value, error identification — **contrast is the design's and ships as authored**) and `kru-visual-reviewer` (the rendered states nobody opens + the cause behind a defect, only once a dev server is actually up — it never starts one; *up* is the port answering, so `curl` it before the batch, since a dev process left alive from an earlier seat can hold on to nothing, and a seat that finds no page falls back to a static read that verifies no rendered criterion). They are report-only and they **do not decide the design**: their findings merge into the same fix list as `kru-code-reviewer`'s, and the PM bot's eye above remains the gate. `references/screen-passes.md` carries how to brief them and the two rules that bound the batch. Skip both for non-UI changes.
- Tests: **first coverage is the builder's**, written test-first during the build (Step 3) — so for a behavior seat the work already arrives tested, and this gate reads the coverage rather than commissioning it. **A screen exemption you named is a slice you owe**: once that intent is settled, dispatch the covering run (the same-task builder, or `kru-test-writer`) — an exemption that closes the loop unclaimed is how "relaxed" turns into "never." Spawn `kru-test-writer` for what that doesn't reach: an **exempted** seat's output, coverage sweeps and fan-out across many files, repairing a red or flaky suite, and any repo whose testing conventions still have to be discovered from scratch. Either way, a scoped test-count check is lead-owned, the list in `SKILL.md` → *Delegate on stack, not size*: see the counts yourself, from a run scoped to the slice's changes — a builder's "tests pass" is a narrative until you have. A full suite runs only when the user asks. A red or flaky suite, a coverage sweep, and a long run are `kru-test-writer`, not this check. **Test credentials:** before any scoped run, `kru-test-writer` dispatch, or Browser check that needs secrets or a database, follow `references/test-credentials.md` and stop the slice on a failed guard.
- UX (journey): when the change lands or reshapes a **multi-screen flow** (signup, checkout, onboarding), spawn `kru-ux-auditor` on the flow by name. It walks the path statically — no browser — and returns findings ordered along the walk. Skip for single-screen or purely visual changes; those are the screen passes' scope — journey-scoped and screen-scoped are different lanes, and `kru-ux-auditor` is the only one that walks between screens. Its `HEURISTIC` findings are questions, not defects — don't hand them to a builder as a fix list.
- Behavior: the Browser subagent to confirm it actually works ([browser](https://cursor.com/docs/agent/tools/browser), [subagents](https://cursor.com/docs/subagents)). Cursor's own `/run` is Shell Mode, an alias of `/shell` ([slash commands](https://cursor.com/docs/cli/reference/slash-commands)), which does not confirm a running product.
- Loop fixes back to the builder**s** — a merged fix list groups by seat exactly as the original change did (*Group the change's files by seat*, Step 3), so a list spanning two seats is two loops, not one brief handed to whichever seat the feature is named after. Findings arrive as `file:line`; contract item 2 (Step 3) converts each to its named anchor before dispatch. Max 2 loops per seat — a third grows one builder's context past its slice. Then the loop stops: surface only what someone using the product would notice, in their terms; the rest is one counted clause, and the full list stays in the report. A remainder the user wants fixed is a new slice for a fresh builder, never a third round.
